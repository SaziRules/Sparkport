SPARKPORT — UX BUYING EXPERIENCE IMPROVEMENT PLAN
==================================================
Goal: Serve users with absolute buying power — fast, trustworthy,
frictionless from first product view to completed order.
==================================================


CURRENT STATE SUMMARY
----------------------
All phases from the original infrastructure/integration plan (Phases 0–9)
are complete: WordPress/WooCommerce API layer is live, products and blog
are dynamic, cart is integrated with WooCommerce Store API v1, CartContext
manages global state, CartDrawer is animated, cart page and product detail
page are fully built.

The buying journey now works end-to-end but has real gaps that affect
conversion and user trust:

  - Add to cart takes 3 sequential network requests (~1.5–3s per click)
  - Button labels are inconsistent across components
  - No instant feedback — user stares at a spinner after clicking
  - No toast / confirmation that anything happened
  - No trust signals, delivery info, or pharmacist cues on product pages
  - No free shipping progress, no urgency, no scarcity signals
  - Cart drawer and cart page are functional but not persuasive
  - No checkout page — "Proceed to Checkout" goes nowhere
  - Micro-copy is generic — no pharmacy voice, no power triggers

PHASE 1 — PERFORMANCE & SPEED
================================================================
Goal: Make add-to-cart feel instant. Fix all slow paths.
Target: <200ms perceived response on every add-to-cart click.

1.1  Fix the 3-request add-to-cart chain
     Current flow (SLOW):
       Click → getFreshNonce() [GET /wc/store/v1/cart]
             → POST /wc/store/v1/cart/add-item
             → fetchCart() [GET /wc/store/v1/cart re-fetch]
     That is 3 sequential server-to-WC round-trips before UI updates.

     Fix in contexts/CartContext.tsx:
       a) Implement optimistic UI — update cart state immediately on click
          before any network request completes. Show the item in the cart,
          increment the badge, open the drawer. If the API fails, roll back.
       b) Cache the nonce in CartContext state. On initial fetchCart(), store
          the nonce returned in response headers via the /api/cart route.
          Pass it to mutations. Only re-fetch a nonce on 403 responses.
       c) For add and update mutations: trust the WC response body (it
          returns the updated cart). Only do a full re-fetch on remove
          where WC sometimes returns CartItem instead of Cart.

     Fix in app/api/cart/add/route.ts and app/api/cart/item/[key]/route.ts:
       Accept an optional nonce from the client request body. If provided
       and valid, skip the getFreshNonce() pre-flight GET. Fall back to
       fetching a fresh nonce only when no client nonce is given or on
       403 from WC.

     Result: add-to-cart drops from 3 requests to 1 in the happy path.
     Optimistic update means the user sees instant feedback regardless.

1.2  Optimistic UI implementation
     In contexts/CartContext.tsx:

     addToCart(productId, quantity):
       1. Build an optimistic CartItem from the product data passed in
       2. setCart(prev => optimisticallyAdd(prev, optimisticItem))
       3. setIsDrawerOpen(true)                  ← drawer opens instantly
       4. Fire the API call in the background
       5. On success: replace optimistic state with real server response
       6. On failure: rollback to previous cart state + show error toast

     updateQuantity(key, quantity):
       1. setCart(prev => optimisticallyUpdate(prev, key, quantity))
       2. Fire API call
       3. On success: sync with real response
       4. On failure: rollback

     removeFromCart(key):
       1. setCart(prev => optimisticallyRemove(prev, key))
       2. Fire API call (keep re-fetch here — WC DELETE is inconsistent)
       3. On failure: rollback

     Helper functions (pure, no side effects):
       optimisticallyAdd(cart, item) → Cart
       optimisticallyUpdate(cart, key, qty) → Cart
       optimisticallyRemove(cart, key) → Cart
       Each recalculates items_count and totals.total_items from items array.

     addToCart signature change:
       addToCart(productId, quantity, productSnapshot?) → Promise<void>
       productSnapshot: { name, price, image, key } — used to build
       the optimistic item. ShopLayout, FeaturedProductsTabs, and
       ProductDetailPage already have the full Product object — pass it.

1.3  Nonce lifecycle in CartContext
     - On initial fetchCart() response: store the nonce from the
       X-WC-Store-API-Nonce or Nonce header (returned by /api/cart route).
       Store in a useRef (not state — nonce changes don't need re-renders).
     - Pass nonceRef.current in the request body of each mutation call
       to the Next.js API routes.
     - API routes: if client provides nonce, skip getFreshNonce() pre-flight.
     - If WC returns 403: CartContext catches it, calls fetchCart() to get
       a fresh nonce, then retries the mutation once.

1.4  Button consistency audit and fix
     Every "Add to Basket" / "Add to Cart" button across the codebase
     must call addToCart with the correct productId and quantity.

     Files to audit and fix:
       components/ShopLayout.tsx
         - Both grid view card button and list view card button call handleAdd
         - Confirm quantity from per-product quantities state is passed
         - Button label: "Add to Basket" (consistent everywhere)
         - Loading state: spinner, disabled, no double-submit
         - Post-add state: green checkmark for 1500ms then reset

       components/FeaturedProductsTabs.tsx
         - handleAdd calls addToCart(product.id, getQty(product.id))
         - Same post-add checkmark state as ShopLayout
         - Confirm all three tab panels (hot-deals, bestsellers, new-arrivals)
           each have working buttons — not just the first active tab

       components/ProductDetailPage.tsx
         - handleAdd calls addToCart(product.id, quantity)
         - Already has isAdding state — extend with isAdded (checkmark phase)
         - Confirm quantity stepper value is always passed

       components/CategorySpotlight.tsx / CategorySpotlightTabs.tsx
         - Audit whether Add to Basket buttons exist and are wired
         - If product cards appear here without Add to Basket: add them

     Post-add button state pattern (apply to all four components):
       idle    → "Add to Basket"         [teal button]
       adding  → spinner + "Adding..."   [teal, disabled]
       added   → checkmark + "Added!"    [green, disabled, 1500ms]
       idle    → back to default

1.5  Cart drawer render performance
     The drawer is always in the DOM (correct — enables CSS transitions).
     Ensure the item list does not re-render expensively when closed.
     Wrap the items list in React.memo or use a conditional render guard
     so the expensive map() only runs when isDrawerOpen is true or items
     have changed. Drawer open/close must feel instant — no jank.

1.6  Image performance in cart and product cards
     In CartDrawer.tsx and app/cart/page.tsx:
       - All item images already use next/image with fill + sizes
       - Add placeholder="blur" with a data URI blurDataURL for instant
         placeholder while image loads (generate a 1x1 pixel in brand color)
     In ShopLayout product cards:
       - Confirm all product images use next/image
       - Add sizes attribute matched to actual rendered size
       - Add loading="eager" for above-the-fold products (first 4),
         "lazy" for the rest

1.7  Identify and remove any unnecessary re-renders
     - CartContext value object is recreated on every render unless memoized
       Wrap the context value in useMemo keyed on cart, isLoading, isDrawerOpen
     - openDrawer and closeDrawer are already useCallback — keep them
     - All mutation functions are already useCallback — keep them

PHASE 7 — CHECKOUT PAGE
================================================================
Goal: Build a complete, conversion-optimised checkout at /checkout.

7.1  Research: WooCommerce Checkout approach
     Two options:
       A) WooCommerce Block Checkout API — POST /wc/store/v1/checkout
          Accepts billing, shipping, payment_method, customer_note.
          Returns order ID and payment URL on success.
          Best for fully custom UI. Requires handling payment methods.
       B) Redirect to WC hosted checkout — pass Cart-Token as query param
          so WC session is linked. User completes payment on the WP site.
          Simpler, handles all payment gateways automatically.
     RECOMMENDATION: Option B for Phase 7 (redirect to WC hosted checkout).
     The WC checkout page can be styled to match Sparkport branding.
     Option A (fully custom checkout) can be built in a future phase once
     the store is live and payment flows are validated.

7.2  Build app/checkout/page.tsx (redirect approach)
     'use client'
     On mount: get Cart-Token from cookie (send via /api/cart/token GET route)
     Redirect user to:
       https://sparkport.co.za/checkout/?add-to-cart=redirect&source=headless
     OR: construct WC checkout URL with session data

     While redirecting: show a full-page loading state
       Sparkport logo centered
       Spinner
       Text: "Taking you to secure checkout..."
       Security badge row at bottom

7.3  New API route: app/api/cart/token/route.ts
     GET: reads wc_cart_token cookie, returns { token: string }
     Used by checkout page to pass session to WC hosted checkout

7.4  Post-checkout success page: app/checkout/success/page.tsx
     Shown after WC redirects back with ?order_id=N&key=wc_order_XXX
     Display:
       Large green checkmark animation
       "Order #{orderId} confirmed!"
       "We'll send a confirmation to your email."
       Order summary (fetch from WC REST API by order key)
       Two CTAs: "Continue Shopping" → /shop, "View Your Account" → /account
     On this page: clear the local cart state (setCart(EMPTY_CART))

BUG REPORT — Full Buying Flow Audit (2026-06-26)
================================================================
Build: clean (npx tsc --noEmit, npm run build — zero errors)
Audit method: full code review of every file in the buying flow

Severity key:
  CRITICAL  — breaks the flow entirely for some/all users
  BUG       — wrong visible behaviour the user can observe
  UX ISSUE  — confusing or misleading but not outright broken
  MINOR     — edge-case or cosmetic problem


----------------------------------------------------------------
CRITICAL
----------------------------------------------------------------

C1. addToCart swallows errors; callers always show "Added!" on failure
    Files: contexts/CartContext.tsx (lines ~185-203)
           components/ProductDetailPage.tsx (~line 43)
           components/ShopLayout.tsx (~line 70)
    Problem: After a failed API call the callback rolls back cart state
    but does NOT re-throw. All callers (ProductDetailPage.handleAdd,
    ShopLayout.handleAdd) unconditionally set isAdded=true after awaiting
    addToCart. Result: the user sees the green "Added!" check and the
    drawer opens — but the item was never added. Silent checkout failure.
    Fix: addToCart should re-throw (or return { success: false }) on
    terminal failure so callers can branch; also call showToast error;
    callers must not set isAdded=true on error.

C2. Same silent-failure pattern applies to updateQuantity and removeFromCart
    File: contexts/CartContext.tsx
    All three mutation callbacks only console.error on failure. Zero user
    feedback for any cart error. The toast infrastructure is wired into
    ClientProviders.tsx but showToast is never called anywhere in the
    cart flow. Every failure — network error, 403, out-of-stock rejection
    — is silent.
    Fix: Wire showToast into all three mutation catch blocks.

C3. Checkout hand-off will break if Next.js app and WooCommerce are on
    different hosts / subdomains
    File: app/checkout/page.tsx
    Problem: wc_cart_token is an HttpOnly cookie set by the Next.js API
    routes on the Next app's host with no explicit Domain attribute (so
    it is host-only). The redirect target is https://sparkport.co.za/
    checkout/. If the Next app is on a different subdomain (e.g.
    app.sparkport.co.za or a Vercel deployment URL), the cookie is NOT
    sent to sparkport.co.za and the WooCommerce checkout loads an empty
    cart. There is no fallback.
    Fix: Confirm deployment: the Next app and WooCommerce must be on the
    same host or the Set-Cookie headers must include a shared Domain=.
    sparkport.co.za attribute. If hosts differ, switch to a server-side
    redirect (Next.js redirect) that passes the session via URL token.

C4. Drawer "Proceed to Checkout" stays enabled during 4s undo window
    File: components/CartDrawer.tsx (~line 137)
    When the user removes their last item, showFooter=true because
    pendingRemoval exists, so the checkout CTA is still clickable. But
    the optimistic cart is now empty (count=0), so clicking "Proceed to
    Checkout" navigates to /checkout → redirects to WC with an empty
    session.
    Fix: Disable / hide the checkout button when activeItems.length === 0,
    even while pendingRemoval is set.


----------------------------------------------------------------
BUG
----------------------------------------------------------------

B1. DeliveryEstimate countdown is off by 1 minute almost always
    File: components/DeliveryEstimate.tsx (~lines 12-25)
    minutesLeft = 59 - minutes is wrong. At 13:00 SAST it shows "0h 59m"
    instead of "1h 0m". At 13:59 it shows "0h 0m" instead of "0h 1m".
    The hours display also wraps incorrectly at the top of each hour
    (shows 0h Xm instead of 1h 0m etc.).
    Fix: Replace with:
      const totalLeft = 14*60 - (hours*60 + minutes);
      const hoursLeft = Math.floor(totalLeft / 60);
      const minutesLeft = totalLeft % 60;

B2. Free delivery progress bar ignores applied discounts/coupons
    File: components/CartDrawer.tsx (~line 28)
    parsedTotal = parseInt(total, 10) / 100 uses the raw item subtotal
    (total_items), not the discounted total. A user with a R600 basket
    and a R150 coupon sees "FREE delivery unlocked!" but their actual
    chargeable total is R450 — below the R500 threshold.
    Fix: Use (parseInt(cartTotals.total_items,10) -
    parseInt(cartTotals.total_discount,10)) / 100 as parsedTotal.
    This requires cartTotals to be destructured from useCart() in
    CartDrawer (it's already exposed by the context).

B3. lastAddedKey highlight timer fires 800ms after optimistic update,
    not after API response — leaves permanent glow on slow connections
    File: contexts/CartContext.tsx (~line 205)
    setTimeout(() => setLastAddedKey(null), 800) is scheduled right after
    setCart(optimisticCart). On a slow connection the API takes > 800ms,
    so the timer clears lastAddedKey before the real cart response sets
    it to the real WC key (line 184/194). After that the lastAddedKey is
    set to the real key but no new timer clears it — the highlight stays
    forever.
    Fix: Move the 800ms clear timer to the success branch (after
    setLastAddedKey(result._key or similar)), not the optimistic branch.

B4. Cart page "Delivery: FREE" shows before user enters any address
    File: app/cart/page.tsx (~line 246)
    shipping === 0 when WC has not yet calculated a shipping rate (no
    address), so the order summary always shows "FREE" delivery before
    checkout. This may set false expectations.
    Fix: Show "Calculated at checkout" when shipping === 0, only show
    "FREE" when a positive qualifying condition is known (e.g. total above
    threshold). Or add a note: "FREE on orders over R500".

B5. Coupon success state never clears; no UI to remove an applied coupon
    File: app/cart/page.tsx (~lines 56-78)
    After a coupon is applied, "Coupon applied!" text stays until the
    user types in the input (onChange resets to idle). There is no way
    for the user to see which coupon is active or to remove it — the
    DELETE route exists but there is no Remove button in the UI.
    Fix: After refreshCart() resolves, reset couponCode to '' and
    couponStatus to 'idle'. Add a "Remove" link/button when discount > 0.

B6. isLoading in CartContext is never set to true on initial fetch
    File: contexts/CartContext.tsx
    The initial useEffect calls fetchCart() but never sets isLoading=true
    before the call or =false after. isLoading only flips during
    mutations (add/update/remove). Result: on first page load, count=0
    and isLoading=false simultaneously, so cart/page.tsx shows the empty-
    cart message briefly for users who have items — until fetchCart
    resolves and count updates.
    Fix: Set isLoading=true before the initial fetchCart() call inside
    the mount effect, and false in the finally block.

B7. handleRemove in CartDrawer does not handle rapid removes on same item
    File: components/CartDrawer.tsx (~lines 116-127)
    If the user clicks Remove, then clicks Remove again on a different
    item within 4s, the first pending removal fires immediately (correct)
    but if removeFromCart fails for the first item it rolls back —
    however the UI is now showing pendingRemoval for item 2. The user
    sees item 1 reappear unexpectedly with no explanation.

B8. Cart page shows "You saved R0.00" lines for non-sale items
    File: app/cart/page.tsx (~line 40)
    savedPerUnit = (regular_price - price)/100. WC returns regular_price
    equal to price when the item is not on sale, but only if the product
    was ever indexed with a sale price. If regular_price is '0' (missing)
    the math gives a negative saving, and if regular_price == price the
    guard savedPerUnit > 0 correctly hides it. However if WC ever returns
    regular_price as '' or null, parseInt gives NaN and the comparison
    NaN > 0 is false — fine. Edge case, but worth a null-coalesce guard.

UX ISSUE
----------------------------------------------------------------

U1. Zero toast feedback across the entire cart flow
    showToast is defined and wired (ClientProviders.tsx line 16) but
    never called. No success confirmation when adding, no error when
    failing, no "Coupon applied!" notification. The toast system built
    in Phase 2 is completely unused.

U2. Drawer opens on failed adds
    contexts/CartContext.tsx (~line 171): openDrawer() is called as part
    of the optimistic update, BEFORE the API result. If the API rejects
    and rolls back, the drawer has already opened and the item disappears
    mid-view with no explanation. Users see the drawer pop, then the item
    vanish — very confusing.

U3. /checkout/success trusts an unvalidated order_id URL param
    File: app/checkout/success/page.tsx
    Any URL /checkout/success?order_id=12345 shows a full "Order #12345
    confirmed!" page and clears the local cart. No order verification
    against WC. A user who bookmarks the URL or receives a bad redirect
    has their cart cleared incorrectly.
    Fix: Either don't display the order_id in the heading (just "Order
    confirmed!") or validate it against the WC REST API.

U4. clearCart() on success page only clears local state, not WC session
    File: app/checkout/success/page.tsx
    setCart(EMPTY_CART) wipes the React state, but the next CartContext
    mount (new page/tab) calls fetchCart() which still returns the old
    WC session cart. If the WC checkout actually cleared the session this
    is fine, but if the session persists (e.g. failed payment, order
    pending), the cart refills.

U5. Qty stepper has no debounce — rapid clicks queue multiple concurrent
    PUT requests that can apply out of order
    File: components/CartDrawer.tsx (~lines 281-299)
    Each +/- click fires updateQuantity immediately. Five rapid clicks
    fire five PUTs; whichever resolves last wins and can set the wrong
    quantity.
    Fix: Debounce qty stepper (200-300ms) or track in-flight requests and
    cancel stale ones.

U6. Drawer suggestions fetch repeats on every open — no caching
    File: components/CartDrawer.tsx (~line 65)
    useEffect fires whenever isDrawerOpen becomes true with count=0.
    Every time the user opens an empty drawer the same 3 products are
    re-fetched from the API.
    Fix: Only fetch once (check suggestions.length > 0 before fetching),
    or store in sessionStorage.

U7. Hard-coded R500 threshold label doesn't use the FREE_DELIVERY_THRESHOLD constant
    File: components/CartDrawer.tsx (~line 360)
    The visible label says "{symbol}500 threshold" as a string literal
    while the actual threshold logic uses FREE_DELIVERY_THRESHOLD = 500.
    If the constant changes the label drifts.
    Fix: Interpolate: `${symbol}${FREE_DELIVERY_THRESHOLD} threshold`

U8. Checkout page analytics event always reports itemCount=0 and total=''
    File: app/checkout/page.tsx (~lines 13-17)
    sparkport:checkout:begin fires with hardcoded empty detail because
    useCart() is not called on that page.
    Fix: Add useCart() to checkout/page.tsx and pass real count/total.

U9. Applied coupon has no removal UI on cart page
    See B5 — the DELETE /api/cart/coupon route exists and works but
    there is no "Remove" button visible to the user once a coupon is
    applied and discount shows in the order summary.
