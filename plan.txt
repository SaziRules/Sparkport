# Sparkport.co.za Production Cutover Plan

> **For agentic workers:** Steps use `- [ ]` syntax for tracking. This is an ops/deployment plan — tasks are phases of a DNS cutover, not code modules. Do phases in order; a failure in one blocks the next.

**Goal:** Replace the current WordPress site at `sparkport.co.za` with the Next.js app in this repo, without breaking checkout, email, product data, or search ranking.

**Architecture:** The Next.js app stays server-rendered (not static). WordPress is not retired — it continues to serve the WooCommerce REST API and remain the source of truth for product and order data, but moves to a subdomain (`shop.sparkport.co.za`). The apex domain is pointed at a Node-capable host (Vercel recommended; Axxess Cloud VPS is the fallback — see Task 2). Axxess continues to own DNS and email.

**Tech Stack:** Next.js 16.1.6 (Node runtime, API routes, `proxy.ts`), Supabase (auth + DB + storage), WooCommerce REST (products/orders), PayFast / PayGate (payments), Brevo (transactional email), Google Maps JS API.

**Spec:** This file. (No prior design doc — the spec is the user's ask: "make Next.js serve sparkport.co.za, replacing WordPress; hosting is Axxess.")

## Global Constraints

- The live store must never be unreachable for more than the DNS TTL window. Lower TTL to 300s at least 48h before cutover.
- MX, SPF, DKIM, DMARC records at the apex MUST be preserved — email runs through Axxess and must keep working.
- WooCommerce stays the product/order system of record. No product data is migrated out of WP in this plan.
- PayFast/PayGate notify URLs and WC webhook destinations MUST be updated in the same change window as DNS, or payments will land on the old WP host and orders will be lost.
- No step may touch the live apex `A` record until Task 7 (pre-cutover QA green on the preview URL).
- Keep a full pre-cutover WP backup (files + DB) for at least 30 days. This is the rollback floor.

## Review Focus

Five things the tasks below do not individually test but will bite you if ignored:

1. **Email silently dies** if the apex `A` swap also wipes MX/TXT records. Check the full zone diff before applying. (Task 7, Step 4.)
2. **PayFast ITN hits the old server** if notify_url isn't updated in the PayFast dashboard before cutover. Orders go into a limbo state. (Task 6, Step 2.)
3. **Supabase auth links break** if the SITE_URL env var still points at `localhost` or the preview URL after cutover. Reset emails and OAuth callbacks fail. (Task 5, Step 2.)
4. **Google loses existing product/blog URLs** if 301s aren't in place. Rankings drop. (Task 9.)
5. **WP admin on the apex breaks** the moment DNS swaps, because the admin now resolves to Vercel. Admin access must move to `shop.sparkport.co.za/wp-admin` (Task 1) *before* cutover, not after.

- [ ] **Step 6 (only if Step 5 shows a redirect to apex):** The usual cause is a canonical-redirect plugin or `.htaccess` rule rewriting the host. Options, in order of preference:

     ```php
     // Allow the REST API to respond on any host that resolves to this install.
     // Does NOT change Site Address — public pages still canonicalise to the apex.
     if ( defined('REST_REQUEST') && REST_REQUEST ) {
         $host = $_SERVER['HTTP_HOST'] ?? '';
         if ( $host === 'shop.sparkport.co.za' ) {
             define('WP_HOME',    'https://shop.sparkport.co.za');
             define('WP_SITEURL', 'https://shop.sparkport.co.za');
         }
     }
     ```

     This makes the REST endpoint honor the Host header *only for REST requests*, leaving normal pageviews canonicalising to the apex.

  2. If you cannot edit `wp-config.php`, install the free plugin **"Multiple Domains"** (by Straightforward) and add `shop.sparkport.co.za` as a secondary domain. Lighter touch, same effect.

  Re-run Step 5. Must be `200` with JSON on both endpoints, no redirect.

- [ ] **Step 2:** For each legacy URL that has a direct Next.js equivalent, add an entry to `redirects()` in `next.config.ts`:

  ```ts

    return [
      { source: '/product-category/:slug', destination: '/categories/:slug', permanent: true },
      { source: '/shop/', destination: '/shop', permanent: true },

  }
  ```

## Rollback plan

If the site is broken post-cutover and the fix isn't quick:

1. In Axxess DNS, restore the apex `A` and `www` `CNAME` to their pre-cutover values (from the snapshot in Task 8 Step 3). Propagation takes up to 300s thanks to the lowered TTL.
2. In PayFast + WC webhooks, revert the URLs noted in Task 6 Step 4.
3. In WP Admin → Settings → General, if you also changed WordPress Address to the subdomain, revert it to the apex.
4. Take a new incident snapshot: which Vercel deploy was live, what the first error was, which page failed. Fix on preview, re-run Task 7, re-cut.

Rollback is cheap because WP never stopped running on `shop.sparkport.co.za` — it still serves the same document root the apex used to.
